前端线：Vite 的墙与两条退路

Vite/esbuild/rollup@4/SWC/tailwind-oxide 全线不可用
退路A webpack+ts-loader 纯JS：10.4s → 260KB bundle，HTTP 200
退路B @rollup/wasm-node：15.5s → 1.35MB，可用作 Vite 生态兼容
WASM 代价：慢 1.5–2.5×，RSS 峰值 481MB；esbuild 无官方 wasm 回退（vite#13208 NOT_PLANNED）

根因：不是签名，是 ELF section header 校验

  • 假说一「SELinux 来源标签」被推翻：自编 ELF 与其 cat 副本标签相同（hmdfs:s0）都能跑
  • 决定性实验：把正常 ELF 的 shdr 偏移字段写坏 8 字节 → 立刻 permission denied
  • 鸿蒙 loader 严格校验 section header；Go 二进制（bad shdr）/Rust native 因此被拒，Linux 宽容
  • HNP / HarmonyBrew bottle 是 OHOS 原生构建 → 不受影响

一次嗅探给你现象，一组对照实验给你根因

摩擦点清单

  • 外来原生二进制被 shdr 校验拦截 → 前端锁定纯 JS/WASM 栈
  • 无部署通道 → 客户端闭环断在最后一环
  • 系统预置无 JVM → 依赖 HarmonyBrew 渠道（装后体验正常）
  • 沙箱 ~ 双根 / hmdfs 属主（git safe.directory）/ /tmp 只读
  • Electron node 的 stderr 噪声、process.platform=ohos optional deps 缺装

结论与建议栈

可投产：Node/Python/Java 后端、C/C++、Redis/SQLite、静态站点、纯 JS/WASM 前端、HAP 编译签名
待解：运行调试通道（外接设备 / hdcd 监听）
建议栈：HNP 系统工具 + HarmonyBrew 用户软件 + webpack 为主、rollup-wasm 备选 + hvigor 直驱；真机运行验证放外部设备
原则：完备度 → 有无问题 → 性能/易用性；判"不可用"前必须穷举渠道 + 项目级实测
